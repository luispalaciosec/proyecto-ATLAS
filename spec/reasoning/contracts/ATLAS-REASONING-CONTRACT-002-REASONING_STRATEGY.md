# Reasoning Strategy Contract

## Purpose

This contract defines the behavior required for every reasoning strategy inside ATLAS.

A Reasoning Strategy represents a specific reasoning algorithm capable of transforming a reasoning request into a reasoning outcome.

The Reasoning Engine coordinates strategies.

Strategies never coordinate themselves.

---

# Responsibilities

Every Reasoning Strategy is responsible for:

- interpreting the reasoning request

- applying one reasoning algorithm

- producing intermediate reasoning steps

- generating evidence

- reporting assumptions

- returning a deterministic reasoning output

Strategies are not responsible for:

- selecting themselves

- calculating confidence

- generating execution traces

- planning

- workflow generation

- runtime execution

---

# Strategy Identity

Every strategy has a unique identity.

Example

```
strategy_id

strategy_name

strategy_version
```

Identity must remain immutable during execution.

---

# Supported Strategy Types

Examples include:

- Sequential Reasoning

- Rule Based Reasoning

- Deductive Reasoning

- Inductive Reasoning

- Abductive Reasoning

- Graph Reasoning

- Tree Search

- Hybrid Reasoning

Future strategies may be added without changing this contract.

---

# Input

Every strategy receives exactly one immutable object.

```
ReasoningRequest
```

The request must never be modified.

---

# Output

Every strategy returns exactly one immutable object.

```
ReasoningOutcome
```

The outcome contains only the reasoning produced by the strategy.

It does not include:

- confidence

- execution metadata

- workflow

- planning

These are generated by higher-level components.

---

# Preconditions

Before execution, every strategy must verify:

- valid request

- supported input

- required context

- supported reasoning domain

If validation fails, execution must stop immediately.

---

# Execution Lifecycle

Every strategy follows the same lifecycle.

```
Receive Request

↓

Validate Input

↓

Analyze Context

↓

Apply Reasoning Algorithm

↓

Generate Evidence

↓

Generate Assumptions

↓

Produce Outcome

↓

Return
```

Strategies may internally perform many iterations.

The observable lifecycle never changes.

---

# Determinism

Strategies must be deterministic.

Equal inputs always produce:

- equal reasoning

- equal evidence

- equal assumptions

- equal outcome

Random behavior is prohibited.

---

# Reasoning Scope

Strategies only solve reasoning.

They never:

- create workflows

- create plans

- schedule tasks

- execute actions

They only explain what was inferred.

---

# Assumptions

Whenever reasoning requires assumptions, the strategy must explicitly expose them.

Hidden assumptions are prohibited.

Each assumption should be independently observable.

---

# Evidence

Strategies should expose all supporting evidence.

Evidence may include:

- facts

- rules

- retrieved knowledge

- logical deductions

Evidence must never be modified after generation.

---

# Outcome Construction

The produced outcome contains:

- inferred conclusions

- evidence

- assumptions

- reasoning steps

- reasoning metadata

The outcome remains immutable after construction.

# Error Handling

Strategies must return standardized reasoning errors.

Possible categories include:

- Invalid Request

- Unsupported Context

- Missing Evidence

- Invalid Rule

- Internal Strategy Error

Strategies never return partial reasoning unless explicitly configured by the engine.

---

# Thread Safety

Strategies must support concurrent execution.

No execution may affect another execution.

Shared mutable state is prohibited.

---

# Stateless Design

Strategies should be stateless.

Execution-specific information belongs exclusively to the current reasoning session.

No reasoning information should persist between executions.

---

# Performance

Strategies should minimize:

- repeated inference

- duplicated evaluations

- unnecessary allocations

Performance optimizations must never change reasoning results.

---

# Extensibility

New reasoning strategies may be added without changing:

- the Reasoning Engine

- existing strategies

- public APIs

The engine discovers strategies through the Strategy Registry.

---

# Observability

Every strategy execution must expose:

- strategy identifier

- execution start

- execution end

- execution duration

- generated assumptions

- generated evidence

- completion status

---

# Architecture Constraints

Every implementation must satisfy:

- deterministic execution

- immutable inputs

- immutable outputs

- isolated execution

- provider independence

- algorithm independence

Violation of these constraints invalidates the implementation.

---

# Dependencies

Strategies may depend on:

- domain rules

- reasoning algorithms

- internal evaluators

- evidence providers

They must never depend directly on:

- Runtime

- Planning Engine

- Workflow Engine

- Execution Engine

These interactions occur only through the Reasoning Engine.

---

# Relationship with Reasoning Engine

The Reasoning Engine owns:

- strategy selection

- lifecycle coordination

- trace generation

- confidence calculation

The strategy owns only reasoning execution.

```
Reasoning Engine

↓

Reasoning Strategy

↓

Reasoning Outcome

↓

Reasoning Engine
```

The engine always remains the orchestrator.

---

# Relationship with Trace

Strategies produce reasoning steps.

The Trace Service transforms those steps into an immutable reasoning trace.

Strategies never build traces directly.

---

# Relationship with Confidence

Strategies never calculate confidence.

Confidence is calculated after reasoning completes by the Confidence Provider.

This guarantees that reasoning algorithms remain independent from confidence algorithms.

---

# Compatibility

Future implementations may replace:

- inference algorithms

- search algorithms

- rule engines

- symbolic processors

without modifying this contract.

Consumers depend only on observable behavior.

---
